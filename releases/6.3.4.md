# 6.3.4 — Separate microphone and system audio, controllable recording quality

Unofficial custom firmware for the **HiDock H1E only**, built on the official H1E 6.3.0 base. It is Sebastián's own build. The number 6.3.4 belongs to this project and is not an official HiDock release.

6.3.4 is the latest recommended build. Its recording core is the same as 6.3.2, which introduced everything in the table below. Section "6.3.2 and 6.3.4" says exactly what 6.3.4 adds.

## What changes compared with official 6.3.0

| | Official 6.3.0 | Custom 6.3.4 |
| --- | --- | --- |
| Channels in the file | One mono track. Your microphone and the system audio are mixed before encoding, so they cannot be pulled apart later | Two channels kept apart: Channel 1 (left) is the microphone, Channel 2 (right) is the system audio |
| Format | No setting | Stereo MP3 or 16-bit stereo WAV, both at 16 kHz |
| MP3 quality | No setting | Total stereo bitrate of 64, 96, 128 or 160 kb/s |
| Level of each source | No setting | Recording gain per channel, 0% to 200%. 0% is silent, 100% leaves the level unchanged |
| Markers | Hardware button | The button still works. A connected app or program can also add a marker, and the dock can add markers on its own from sound level |
| New quality, gain and automatic-marker settings | No equivalent recording controls | Stored on the dock and used by native recording |

## What you can do with it

- Record your microphone and the call audio separately, so you can mix, clean up or discard either one later. The firmware writes one stereo file. Splitting it into two synchronized mono files is a feature of the HiDock Next app, not of the firmware.
- Raise one voice without touching the other. Set the microphone to 150% and leave system audio at 100%, or set a channel to 0% when you do not want it in the file.
- Leave automatic markers off, which is the fallback when no rule is stored, and turn them on only for the recordings where you want them.

## Quality and storage

Sizes are for stereo at 16 kHz, with 1 MB = 1,000,000 bytes. They are estimates of the audio data and leave out file headers, footers and markers.

| Setting | Total rate | Per hour | Per minute |
| --- | --- | --- | --- |
| MP3 profile 0 | 64 kb/s | 28.8 MB | 0.48 MB |
| MP3 profile 1 | 96 kb/s | 43.2 MB | 0.72 MB |
| MP3 profile 2 | 128 kb/s | 57.6 MB | 0.96 MB |
| MP3 profile 3 | 160 kb/s | 72 MB | 1.2 MB |
| WAV, 16-bit PCM | 64 kB/s (512 kb/s) | 230.4 MB | 3.84 MB |

The MP3 rate is the total for both channels, not a rate per channel. WAV is uncompressed and takes four times the space of MP3 at 128 kb/s.

## Markers

Three sources can put a marker into a recording, and all of them are saved in the file footer when the recording closes.

- The hardware button, as on official firmware.
- A connected app or program, which marks the recording that is active at that moment. An acknowledgement from the dock does not prove the marker was saved. Check the finished file.
- Automatic rules, which run inside the dock without any app.

An automatic rule watches the first channel, the second channel or either one. It fires when the average absolute sound level reaches your threshold (1 to 32767). The sound has to hold for 100 ms, it re-arms after 100 ms of quiet, and markers are at least 10 seconds apart. The rule measures loudness. It does not recognize speech or speakers. It reads the audio before gain, so setting a channel to 0% does not stop that channel from triggering markers. Pick the lane you want, or turn the rule off.

## Exact behavior and limits

- Settings change only while the dock is idle (no recording and no live capture), and they apply to the next recording.
- Gain above 100% can clip.
- Gain affects the saved recording only. It does not change USB conferencing volume or the microphone mute.
- If a stored setting is missing or unreadable, the dock falls back to MP3 with automatic markers off.
- The system-audio lane was confirmed on a dock. The microphone lane follows the dock's wiring and the firmware's mic-mute path. No separate microphone test tone was played. This is not raw capture of each physical microphone in the array.
- The mapping covers normal USB recording. No claim is made for every Bluetooth mode.
- This custom update adds recording controls and markers; transcription remains an application service.

## Checked on a dock

On 6.3.4:

- A 1 kHz tone played to the dock appeared on Channel 2 about 775 times stronger than on Channel 1 (57.8 dB).
- After the update the dock rebooted on its own, all 586 recordings kept their names and sizes, and the stored profile, format and marker settings read back unchanged (MP3, 128 kb/s, both gains 100%, automatic markers off).

On 6.3.2, whose recording code 6.3.4 carries unchanged:

- A 64 kb/s MP3 capture decoded as 16 kHz stereo. A WAV capture decoded as 16-bit stereo at 512 kb/s.
- Muting one channel left the other channel's audio intact in separate WAV captures, in both directions.
- Programmatic and automatic markers were read back from finished files.
- A recording kept running with the app fully closed.

## USB handling and file-list repairs carried forward

These changes were introduced in 6.3.2 and are retained in 6.3.4. They affect communication and file handling; they do not introduce a new audio encoder.

| Change | What it means for you |
| --- | --- |
| USB requests are checked before use: framing, lengths, paths and arithmetic | A malformed request is refused, or dropped with no reply. A client must treat a timeout as a failure |
| File names in commands limited to 1 to 27 printable ASCII characters, with no path separators, colon or `..` | A command cannot point outside the recordings folder |
| Multi-part requests read their full 32-bit sequence and length | Long transfers are tracked correctly |
| File-list entries have their reserved bytes zeroed | Leftover memory no longer shows up in the list |
| The checksum over the start of a file covers the bytes actually read | Files shorter than a read block, such as 1, 511, 513 or 1023 bytes, previously got a wrong checksum from stale buffer data |
| Several console configuration commands reject missing or null arguments | They return an error instead of acting on bad input |
| Memory held for a multi-part request is released on errors, aborts and cleanup | Failed requests no longer leave buffers behind |

The dock also gains a small read-only console report: help, version and uptime. It is not a shell and does not expose the serial port.

These repairs were checked by running the patched firmware code against 377 bounded request/parser cases offline, including malformed inputs. They have not been tried case by case on a dock. The image has booted and recorded on a physical dock.
